# CLAUDE.md — Rules for building SurveyDoctor

Read `BLUEPRINT.md` before every task. It is the source of truth for scope, module specs, tests and the stage plan.

## How to work

- Implement one stage per session, exactly as specified in BLUEPRINT.md §9. Backend commands run from `backend/`, frontend commands from `frontend/`.
- Write complete, working files. Do not leave TODOs or placeholder logic in delivered code.
- Use established libraries (BLUEPRINT.md §3). Do not reimplement algorithms that a listed library already provides, unless the blueprint says so.
- Ask before adding any dependency not listed in BLUEPRINT.md §3.
- Use type hints and docstrings. Each statistical function's docstring explains, in plain English, what it measures, which direction means "worse", and its limitations.
- Keep functions small and testable. No statistics in `backend/api/` or `frontend/`: the API calls `surveydoctor.pipeline`, and the frontend only displays API results.
- Frontend: write the design plan to `docs/design.md` and wait for the owner's approval before writing any styling code. Use the frontend-design skill if it is installed. Regenerate `frontend/src/api/schema.ts` whenever API models change.

## Honesty rules (non-negotiable)

- Never claim a test passed, a value matched R, or a result was produced unless you actually ran it in this session and can show the output.
- Never invent numbers for the README, docs, G*Power fixtures or evaluation summaries. Results come only from files generated by running code.
- If a reference comparison fails, report the mismatch and its likely cause in `docs/validation.md`. Do not loosen tolerances to force a pass.
- Items marked [VERIFY] in the blueprint must not be treated as confirmed until the owner records them in `docs/verification_log.md`.

## Scope

- Do not build anything listed in BLUEPRINT.md §1.2 (v2 features), even if it seems quick.
- If a spec is ambiguous, choose the simplest correct option, record it in `docs/decisions.md`, and mention it in your summary.

## End of every session

1. Run `pytest` and show the real output.
2. Summarise what you built in under 15 lines of plain English.
3. List anything you could not verify and anything the owner must do (commands, downloads, decisions).
4. Give the owner the exact commands for their check, and what success looks like.
